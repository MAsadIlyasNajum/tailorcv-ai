# TailorCV AI — MVP 2 Implementation Plan

## 1. Executive Summary

MVP 2 transforms TailorCV AI from a single-resume, single-analysis validator into a repeatable professional tool: multiple resumes, job-application history, editable AI suggestions, copy/share, improved ATS scoring, analytics, and polished UI. Android-first, local-first, no custom backend.

**Critical scope decision:** Override existing `MVP_2_IMPLEMENTATION_PLAN.md` (Professional Experience-only) and `.kilo/PROJECT_MEMORY.md` single-resume boundaries. The approved MVP 2 scope is the broad multi-resume/history platform defined in the planning prompt.

---

## 2. Key Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| 1 | **Storage:** Extend MMKV to structured multi-key schema. MMKV handles complex JSON; no new dependency needed. | Avoids SQLite/Realm overhead. MMKV proven in MVP 1. |
| 2 | **Data model:** `Resume`, `JobApplication`, `AnalysisResult` as first-class entities. History is derived from `JobApplication` + `AnalysisResult`. | Matches user workflow: "I applied to 15 jobs this month." |
| 3 | **Store refactor:** Replace single-state Zustand store with collection-based store (`resumes[]`, `jobApplications[]`, `currentResumeId`, `currentJobApplicationId`). | Required for multi-resume/history. Every screen touches the store. |
| 4 | **Migration:** Auto-migrate old single-snapshot to new schema on first launch. Preserve all MVP 1 data. | Existing users upgrade without data loss. |
| 5 | **Edit suggestions:** Preserve AI original + store user edits in `userEditedSuggestions` map on `AnalysisResult`. | History stays truthful; users can reset to AI original. |
| 6 | **Professional Experience:** Reintroduce `ExperienceEditorScreen` as part of resume management. Existing code is ready. | Fits multi-resume model naturally; avoids dead code. |
| 7 | **Analytics:** Recommend Sentry (crash reporting) + lightweight event logging. No raw resume/JD/AI content in any event. | Minimum useful implementation; respects privacy. |
| 8 | **Copy/Share:** Expand existing clipboard copy + add `Share` API (built-in RN) for full analysis. | No new package needed for share. |
| 9 | **ATS Score:** Keep "Resume Match" terminology. Add deterministic keyword coverage % alongside AI score for explainability. | Addresses score reliability without overclaiming. |
| 10 | **Navigation:** Tab-based Home/Resumes/History + stack for detail/edit flows. | Simplest structure supporting all features. |

## 3. Current Architecture Audit

### What exists (MVP 1)
- **Screens:** Home, UploadResume, JobDescription, AnalysisResult, FinalResumeOutput, Settings
- **Store:** Single `useResumeStore` — one resume, one JD, one analysis
- **Persistence:** One MMKV key `latest-analysis` storing a single `ResumeStateSnapshot`
- **AI:** `GeminiService` with 3 prompts (analysis, experience improvement, final output). Only analysis is wired to UI.
- **Types:** `AnalysisResult` already has `resumeId`, `jobTitle`, `company` (unused). `ResumeMetadata` tracks PDF info.
- **Professional Experience:** Full `ExperienceEditorScreen` + store CRUD + AI method, all commented out/deferred.
- **Tests:** 12 suites / 30 tests covering parsers, validation, store persistence, screens.

### What breaks with MVP 2 scope
- Single MMKV snapshot cannot represent multiple resumes/history.
- Single `resumeText` / `jobDescription` store fields cannot represent multiple job applications.
- `AnalysisResult` needs `jobApplicationId` and edit tracking.
- Navigation needs new routes for resume manager, history, edit suggestions.
- `HomeScreen` assumes one latest analysis card.

## 4. Data Model

### Resume
```typescript
interface Resume {
  id: string;
  name: string;
  sourceType: 'pdf' | 'text';
  text: string;
  metadata: {
    uri?: string;
    fileName?: string;
    fileSize?: number;
    mimeType?: string;
    extension?: string;
  };
  professionalExperiences: ProfessionalExperience[];
  createdAt: number;
  updatedAt: number;
  lastUsedAt: number;
}
```
- **Required:** id, name, sourceType, text, createdAt, updatedAt
- **Optional:** metadata (for PDFs), professionalExperiences, lastUsedAt
- **Rationale:** Minimal fields. `name` is user-facing. `sourceType` enables different UI paths.

### JobApplication
```typescript
interface JobApplication {
  id: string;
  resumeId: string;
  jobDescription: string;
  companyName?: string;
  jobTitle?: string;
  status: 'active' | 'archived';
  createdAt: number;
  updatedAt: number;
}
```
- **Required:** id, resumeId, jobDescription, status, createdAt, updatedAt
- **Optional:** companyName, jobTitle
- **Rationale:** Required fields keep model simple. Optional fields let users add context without friction.

### AnalysisResult (extend existing)
```typescript
interface AnalysisResult {
  id: string;
  resumeId: string;
  jobApplicationId: string;
  jobDescription: string;        // snapshot at analysis time
  companyName?: string;
  jobTitle?: string;
  matchScore: number;
  matchingKeywords: string[];
  missingKeywords: string[];
  suggestedSummary: string;
  suggestedSkills: string[];
  experienceImprovements: ExperienceImprovement[];
  atsTips: string[];
  userEditedSuggestions?: {
    suggestedSummary?: string;
    suggestedSkills?: string[];
    experienceImprovements?: ExperienceImprovement[];
    atsTips?: string[];
  };
  createdAt: number;
  updatedAt: number;
}
```
- **Required:** id, resumeId, jobApplicationId, jobDescription, matchScore, keywords, suggestions, createdAt, updatedAt
- **Optional:** companyName, jobTitle, userEditedSuggestions
- **Rationale:** `jobApplicationId` links analysis to a saved application. `userEditedSuggestions` preserves AI originals.

### History
- **No separate entity.** History is the set of `JobApplication`s with their linked `AnalysisResult`s, sorted by `updatedAt` desc.

## 5. Persistence & Migration Strategy

### New MMKV Schema
| Key | Type | Purpose |
|-----|------|---------|
| `resumes` | `Resume[]` | All saved resumes |
| `job-applications` | `JobApplication[]` | All saved job applications |
| `analysis-results` | `AnalysisResult[]` | All analysis results |
| `current-resume-id` | `string \| null` | Active resume |
| `current-job-application-id` | `string \| null` | Active job application |
| `current-analysis-id` | `string \| null` | Currently viewed analysis |

### Migration (Phase 0)
1. On app mount, check for legacy key `latest-analysis`.
2. If legacy exists and new keys are empty:
   - Create one `Resume` from legacy `resumeText` + `resumeMetadata`.
   - Create one `JobApplication` from legacy `jobDescription` + `analysisResult`.
   - Create one `AnalysisResult` from legacy `analysisResult` (add `resumeId`, `jobApplicationId`).
   - Save to new keys.
   - Delete `latest-analysis`.
3. If new keys exist, skip migration.
4. If neither exists, start fresh.

### Storage Module Changes
- `src/services/storage/storage.ts` → expand to multi-key CRUD.
- Keep defensive JSON parsing / try-catch.

## 8. Implementation Phases

### Phase 0 — Architecture Audit & Migration Foundation
- **Objective:** Understand current state, plan migration.
- **Actions:**
  1. Audit store, types, screens, persistence, tests.
  2. Define new data model (section 4).
  3. Design MMKV multi-key schema.
  4. Plan store refactor boundaries.
- **Files:** `src/types/resume.ts`, `src/services/storage/storage.ts`, `src/store/useResumeStore.ts`
- **Risk:** Medium. Store refactor touches every screen.
- **Test:** Migration unit test (old snapshot → new entities).

### Phase 1 — Data Model & Persistence
- **Objective:** Implement new types, storage, and migration.
- **Actions:**
  1. Extend `src/types/resume.ts` with `Resume`, `JobApplication`, extended `AnalysisResult`.
  2. Refactor `src/services/storage/storage.ts` to multi-key CRUD.
  3. Add migration logic in `App.tsx` or storage module.
  4. Update `ResumeStateSnapshot` type or deprecate it.
- **Files:** `src/types/resume.ts`, `src/services/storage/storage.ts`, `App.tsx`
- **Risk:** Medium. Migration bugs can lose user data.
- **Test:** Migration integration test, storage unit tests.

### Phase 2 — Store Refactor
- **Objective:** Replace single-state store with collection-based store.
- **Actions:**
  1. Refactor `src/store/useResumeStore.ts` to `resumes[]`, `jobApplications[]`, `currentResumeId`, `currentJobApplicationId`, `currentAnalysisResult`.
  2. Add CRUD actions: `addResume`, `updateResume`, `removeResume`, `setCurrentResume`, `addJobApplication`, etc.
  3. Update all screens to read from collections.
  4. Update `hydrateLatest` to restore collections.
- **Files:** `src/store/useResumeStore.ts`, all screens, all tests
- **Risk:** High. Every screen and test depends on store shape.
- **Test:** Store unit tests, all screen tests updated.

### Phase 3 — Resume Management
- **Objective:** Users can manage multiple resumes.
- **Actions:**
  1. Update `HomeScreen` to show current resume selector.
  2. Build `ResumesScreen` (list, add, delete, rename).
  3. Update `UploadResumeScreen` to support add/edit mode (resumeId param).
  4. Reintroduce `ExperienceEditorScreen` (uncomment navigator + route).
  5. Add resume deletion safety: warn if resume has associated analyses; allow dissociate or cascade-delete.
- **Files:** `src/screens/HomeScreen.tsx`, `src/screens/UploadResumeScreen.tsx`, `src/screens/ExperienceEditorScreen.tsx`, `src/app/navigation/AppNavigator.tsx`, `src/constants/routes.ts`
- **Risk:** Medium. Deletion policy affects history integrity.
- **Test:** Resume CRUD tests, deletion behavior tests.

### Phase 4 — Job Applications & Analysis History
- **Objective:** Users can save job applications and view history.
- **Actions:**
  1. Update `JobDescriptionScreen` to create/update `JobApplication`.
  2. Build `HistoryScreen` (list of job applications with scores/dates).
  3. Build `JobApplicationDetailScreen` (view JD, analysis, associated resume).
  4. Update `AnalysisResultScreen` to receive `analysisId` and load from store.
  5. Deep-link navigation: History → JobApplicationDetail → AnalysisResult.
- **Files:** `src/screens/JobDescriptionScreen.tsx`, `src/screens/AnalysisResultScreen.tsx`, new screens, navigator
- **Risk:** Medium. New screens + navigation changes.
- **Test:** History screen tests, navigation integration tests.

### Phase 5 — Editable AI Suggestions
- **Objective:** Users can edit AI-generated recommendations without corrupting history.
- **Actions:**
  1. Extend `AnalysisResult` with `userEditedSuggestions`.
  2. Build `EditSuggestionsScreen` (edit summary, skills, improvements, tips).
  3. Store edits separately; display edited version with "Reset to AI original" option.
  4. Persist edits to `AnalysisResult.updatedAt`.
- **Files:** `src/types/resume.ts`, `src/store/useResumeStore.ts`, new screen, navigator
- **Risk:** Low. Isolated feature.
- **Test:** Edit/save/reset tests, persistence tests.

### Phase 6 — Copy & Share
- **Objective:** Improved copy/share of results.
- **Actions:**
  1. Add copy buttons per section in `AnalysisResultScreen` (skills, tips, individual improvements).
  2. Add `Share` action using React Native `Share` API.
  3. Add "Copy full analysis" combining all sections.
- **Files:** `src/screens/AnalysisResultScreen.tsx`, `src/screens/EditSuggestionsScreen.tsx`
- **Risk:** Low. Clipboard and Share are built-in RN APIs.
- **Test:** Clipboard integration tests (mock), share intent tests.

### Phase 7 — Resume Match / ATS Improvement
- **Objective:** More explainable and useful scoring.
- **Actions:**
  1. Add `keywordCoverageScore` (deterministic: matching / (matching + missing)).
  2. Display both "Resume Match" (AI) and "Keyword Coverage" (%) in `AnalysisResultScreen`.
  3. Update prompt to request score breakdown rationale (without guaranteeing ATS success).
- **Files:** `src/types/resume.ts`, `src/services/ai/promptBuilder.ts`, `src/services/ai/analysisParser.ts`, `src/screens/AnalysisResultScreen.tsx`
- **Risk:** Medium. Prompt/parser changes affect AI output contract.
- **Test:** Parser tests, UI rendering tests.

### Phase 8 — UI Polish & Animations
- **Objective:** Professional feel, subtle animations.
- **Actions:**
  1. Add `Reanimated` transitions for tab switches and screen pushes.
  2. Polish empty states, loading skeletons, error states.
  3. Improve card hierarchy and spacing consistency.
  4. Add micro-interactions (button press, card tap).
- **Files:** All screens, `src/app/theme/theme.ts`, navigator options
- **Risk:** Low. Visual-only changes.
- **Test:** Snapshot tests where applicable, manual visual QA.

### Phase 9 — Analytics & Crash Reporting
- **Objective:** Minimum useful observability without raw data exposure.
- **Actions:**
  1. Integrate Sentry SDK (crash reporting).
  2. Implement internal event tracker (local-first events with optional export).
  3. Track: `app_opened`, `resume_added`, `resume_selected`, `analysis_started`, `analysis_completed`, `analysis_failed`, `analysis_viewed`, `history_opened`, `resume_deleted`, `analysis_deleted`, `suggestion_edited`, `result_copied`, `result_shared`.
  4. Ensure NO raw resume text, JD, AI responses, or PII in any event.
- **Files:** New `src/services/analytics/`, `App.tsx`, screens
- **Risk:** Low. Additive integration.
- **Test:** Event tracker unit tests, verify no sensitive data in events.

### Phase 10 — Testing & Validation
- **Objective:** Ensure MVP 1 regression protection + MVP 2 correctness.
- **Actions:**
  1. Update all existing tests for new store shape.
  2. Add new tests for: resume CRUD, job application CRUD, history sorting, migration, editing, copy/share, analytics privacy.
  3. Run gates: `npx tsc --noEmit`, `npm test`, `npm run lint`, Android build.
- **Files:** `__tests__/` (all files)
- **Risk:** Medium. Large test surface.
- **Test:** Full suite pass.

## 15. Decisions Required

| # | Decision | Why It Matters | Recommended Option | Alternatives | Impact if Changed Later |
|---|----------|---------------|-------------------|--------------|------------------------|
| 1 | Resume deletion policy | Affects history integrity when a resume is deleted | Dissociate: analyses remain but show "Resume deleted" | Cascade delete analyses | Re-associating deleted resumes requires complex restore |
| 2 | Edit suggestions UX | Determines whether history remains truthful | Separate `userEditedSuggestions` field + reset button | In-place edit overwriting AI original | Users cannot distinguish AI vs. edited content |
| 3 | Analytics service | Determines observability + privacy posture | Sentry (crash) + internal event tracker (lightweight) | Firebase Analytics, Amplitude | Heavy SDKs add size/complexity; Firebase adds backend dependency |
| 4 | Professional Experience scope | Determines if existing deferred code is activated | Include in MVP 2 as part of resume management | Keep deferred to MVP 3 | Existing code is ready; excluding it wastes implementation |
| 5 | History retention policy | Affects MMKV growth over time | Auto-archive applications >90 days; user can clear history | Unlimited retention, fixed limit | Unbounded growth risks storage limits |

1. **Phase 0:** Audit + design finalization
2. **Phase 1:** Data model + persistence + migration
3. **Phase 2:** Store refactor (foundation for everything else)
4. **Phase 3:** Resume management (unlocks primary workflow)
5. **Phase 4:** Job applications + history
6. **Phase 5:** Editable suggestions
7. **Phase 6:** Copy/share
8. **Phase 7:** ATS scoring improvement
9. **Phase 8:** UI polish + animations
10. **Phase 9:** Analytics + crash reporting
11. **Phase 10:** Testing + validation

This order minimizes risk: data layer first, then UI, then observability. Each phase produces a testable increment.
